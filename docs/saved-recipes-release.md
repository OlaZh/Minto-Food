# Збережені рецепти: запуск і перевірка

Реалізація підготовлена локально поверх погодженого відкату. Робоча база та сайт
нову функцію ще не отримали. Старі застосовані SQL-файли залишаються історією;
повторно застосовувати міграцію `recipe_attachments` не потрібно.

## Запуск

1. У Supabase SQL Editor виконати **весь** файл
   `supabase/migrations/20260924_1200_saved_recipes.sql`.
   Він додає `recipes.entry_type`, приватні джерела й bucket `recipe-sources`.
   Чинні рецепти отримують `manual`. Наявне поле виду страви `type` не змінюється.
2. Виконати `supabase/checks/saved_recipes_postflight.sql`.
   Кожне значення результату має бути `true`.
3. Опублікувати підготовлені зміни сайту/API разом із кодом попереднього відкату.
   SQL має бути застосований раніше нового клієнта. Для API й наявного щоденного
   cron потрібні чинні `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET`.
4. Перевірити сценарії нижче у власному тестовому акаунті, а приватність — також
   в іншому акаунті та без входу.

## Що реалізовано

- «Додати рецепт» → «Ввести вручну» / «Додати скріншот».
- Чинна ручна форма, її поля, розрахунок поживності й модерація головного фото
  зберігають попередню поведінку.
- Коротка форма: назва, посилання, фото до 10 МБ / відео до 50 МБ,
  вибір одного фотообкладинки або placeholder, наявний вибір книг.
  Посилання та файли можуть співіснувати. Нових лімітів кількості файлів немає.
  Виправлено втрату вибраних книг після розгортання/згортання спільного переліку.
- Збереження назви, приватного джерела й зв'язків із книгами атомарне.
  Повтор після втраченої відповіді використовує той самий запис.
- «Перетворити на рецепт» відкриває ручну форму з назвою та розгорнутим
  «Оригіналом». Є згортання, перегляд відео, збільшення фото пальцями/кнопками
  та копіювання підказки для ШІ. Джерела нікуди автоматично не надсилаються.
- Збереження перетворення оновлює наявний ID; книги й приватні оригінали
  зберігаються. Скасування не змінює тип запису.
- Джерела й тимчасові посилання на них не зберігаються у публічних полях рецепта,
  SEO або відповіді API збереження. Власниця бачить «Джерело» в перегляді,
  редагуванні та на сторінці свого опублікованого рецепта.
- Screenshot-обкладинка не стає головним фото ручного рецепта автоматично.
  Збережений запис неможливо опублікувати або додати до чужої книги прямим запитом.

## Зберігання і очищення

`recipe_sources` — допоміжний приватний запис, не друга таблиця рецептів.
Файли лежать за шляхом `owner UUID/source UUID/file UUID`. Завантажені об'єкти
незмінні; база перевіряє їхні фактичні метадані розміру та MIME, належність
власниці й те, що обкладинка є фото зі списку файлів. RLS не дає гостям,
іншим користувачам або звичайним сесіям модераторів читати джерела.

Наявний щоденний GDPR cron також очищає приватні джерела через **Storage API**:

- після видалення рецепта метадані папки залишаються до успішного очищення;
- видалені з форми файли позначаються для очищення після збереження;
- незавершені нові завантаження та файли невдалого редагування, які не входять
  у збережений список, прибираються після 24 годин;
- перед остаточним видаленням акаунта прибираються всі його джерела,
  включно з оригіналами вже публічних рецептів.

Помилка Storage залишає метадані для повтору. FK блокує остаточне видалення
профілю до завершення очищення. SQL не видаляє рядки `storage.objects`.
Звичайні підписані URL діють 5 хвилин; їхні DOM-елементи прибираються при виході.

## Перевірки

Команди з кореня репозиторію:

```powershell
node --no-warnings scripts/saved-recipe-sql-check.mjs
node --no-warnings --test scripts/saved-recipe-api-check.mjs
node --no-warnings scripts/save-recipe-check.mjs
node --no-warnings --test scripts/gdpr-cron-check.mjs
node scripts/lint-api.cjs
node node_modules/sass/sass.js scss/main.scss css/main.css --style compressed --quiet
```

SQL-тест використовує наявну локальну інсталяцію PGlite
`node_modules/.cache/recipe-media-qa/node_modules/@electric-sql/pglite`.

Залишено 24 сценарії SQL і 9 API/очищення: приватність, збереження без дублів,
перетворення того самого запису, обмеження файлів і збереження даних при помилках.
Також є 30 чинних перевірок ручного збереження й 4 перевірки захисту cron.
Це локальні перевірки: SQL працює на PGlite, API — з імітацією зовнішніх запитів.
Інтерфейс, робочий Supabase, передача/відтворення відео та розгорнутий cron
ними не перевіряються.

Після запуску перевірити: посилання + фото + відео; вибране фотообкладинку й
placeholder; одну/дві/типову книгу; скасування та збереження перетворення;
той самий ID та книги; приватність джерел після публікації; очищення тестового
рецепта/акаунта. Приватність перевіряти також прямими запитами з чужим JWT.

## Відкат нової функції

`supabase/migrations/20260924_1200_saved_recipes_rollback.sql` навмисно
відмовляється виконуватись, якщо лишилися збережені записи, джерела або файли.
Він не призначений для видалення користувацьких даних. Порожній bucket перед
відкатом видаляється через Storage Dashboard/API. Після SQL потрібен сумісний
відкат нового клієнта/API; стару систему `recipe_attachments` відновлювати не слід.
