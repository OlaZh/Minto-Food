## Supabase

SQL-відкат застосований користувачкою в Supabase. Наданий результат фінальної
перевірки містить `true` для всіх 17 показників: таблиці, колонки, RPC вкладень
і порожній bucket прибрані; оригінальна GDPR-функція та її права відновлені;
наявні функції схвалення й відхилення правок збережені.

Перед відкатом перевірка показала `attachment_records = 0` і `stored_files = 0`.
Перший запуск зупинився на перевірці наявності bucket, без застосування змін.
Після видалення порожнього `recipe-attachments` користувачка повторила весь
SQL і надала успішний результат. Підтвердження базується на цьому результаті;
незалежного доступу агента до робочої БД немає: REST повернув HTTP 401,
Storage — AccessDenied, браузер — `missing field sandboxPolicy`.

Нижче збережено порядок виконання для історії. Повторно запускати вже
застосований SQL-відкат не потрібно. Залишилося опублікувати повернутий код
основного сайту й адмінки; локальні зміни ще не закомічені.

1. Зробити резервну копію БД у Supabase; перевірити відкат на staging-копії,

   очищення. Якщо такі дані є — спочатку визначити їхню долю.
   Підготовлений SQL відмовиться їх видаляти.
3. Коли сховище порожнє і немає таких даних, видалити тільки порожній bucket

   SQL-транзакції відкочуються; видалення bucket — окрема попередня операція.
5. Узгоджено розгорнути повернуті основний сайт та адмінку. Старий інтерфейс

Записи Storage не видаляються SQL: це лише метадані, тому операції з файлами
