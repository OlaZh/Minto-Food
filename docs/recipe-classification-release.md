# Комбінована класифікація рецептів

Користувач обирає категорію та, за бажанням, тип страви й метод приготування.
«Салат» доступний у типі страви; окрему категорію «Салат» прибрано.
Адміністратор має такі самі списки, окреме необов'язкове поле «Кухня» та
дієтичні/побутові теги з наявними автопідказками. Теги використовують `tags.code`,
як і каталог; робоча таблиця не має колонки `slug`.

## Застосування

1. `supabase/migrations/20260929_1100_recipe_classification.sql` уже застосована
   користувачем 30.09.2026: повідомлено `Success. No rows returned`.
   Повторно міграцію не виконувати.
   SQL додає `recipes.cuisine` й підтримку типу/методу в атомарному
   `stage_recipe_update`. Без цього кухня не збережеться, а нові поля не
   збережуться при редагуванні опублікованого рецепта.
2. `supabase/checks/recipe_classification_postflight.sql` виконано користувачем:
   усі чотири структурні перевірки повернули `true`. У другому результаті
   спочатку було 180 рецептів зі старими значеннями; розширений результат
   із назвами, текстом інгредієнтів і кроками містить уже 177 записів.
   Вони переглянуті; [точні пропозиції](recipe-classification-review.md)
   підготовлені для погодження. Повторно запускати міграцію не потрібно.
   SELECT лише читає дані; перекласифікація потребує погоджених відповідників.
3. Розгорнути сайт/API й адмінку.

Міграція переносить шість наявних кухонь із категорії в `cuisine`. Категорію
залишає порожньою, якщо її неможливо однозначно взяти зі старого типу.
Старі типи «сніданок/обід/вечеря/перекус/десерт/напій/випічка» переходять
у відповідну категорію лише без конфлікту з уже записаною категорією.
Категорія «Салат» переходить у тип «Салат» лише якщо тип порожній або вже «Салат».
Сім точних відповідників методів (`boiled` → `boiling`, `raw` → `fresh` тощо)
нормалізуються. `slow_cooked`, `fit`, `vegan` і суперечливі класифікації
зберігаються для ручної перевірки; інші поля рецепта не змінюються.

Оригінальні змінені значення й визначення RPC зберігаються в службових
таблицях `recipe_classification_20260929_*`, недоступних клієнтським ролям.
Міграція одноразова. Файл `_rollback.sql` відновлює їх після відкату коду
та зупиняється, якщо це могло б стерти подальші зміни або нові дані про кухню.
Для destructive відкату діють правила `supabase/migrations/README.md`.

## Перевірки

```powershell
node --no-warnings scripts/recipe-classification-check.mjs
npm.cmd run test:save-recipe
node --no-warnings --test scripts/saved-recipe-api-check.mjs
```

SQL-перевірка використовує ту саму локальну PGlite, що й
`scripts/saved-recipe-sql-check.mjs`. Якщо її ще немає:

```powershell
npm.cmd install --prefix node_modules/.cache/recipe-media-qa @electric-sql/pglite@0.5.8
```

Перевірені узгодженість списків, коди автотегів, збереження й очищення нових
полів, передача їх у published-edit RPC, права доступу, перенесення старих
класифікацій та захищений від втрати подальших правок відкат. Локальна
браузерна перевірка використала справжній HTML форми й обробники селектів:
320/390/1280 px, UA/PL/EN, світла/темна тема. Авторизація та робоча база
в цій браузерній перевірці не використовувалися.

Застосування міграції підтверджене користувачем 30.09.2026. Додаткова
перевірка `recipes?select=cuisine&limit=0` повернула HTTP 200: нове поле
доступне через REST API. Ця перевірка не читала й не змінювала рецепти.
Користувач також надав результат postflight: `cuisine_column`,
`rpc_saves_method`, `service_can_save`, `client_cannot_call_rpc` — усі `true`.
Це підтверджує наявність поля кухні, згадки методу у визначенні RPC та
перевірених прав виконання; це не перевірка збереження через робочий інтерфейс.
Розгортання нового коду сайту/API й адмінки ще не підтверджене.

## Залишкові старі значення

Перший прикріплений користувачем результат містив 180 унікальних рецептів:

| Поле | Кількість рецептів | Значення поза поточними списками |
| --- | ---: | --- |
| Категорія | 57 | `side_dish` (24), `combo` (10), `salad` (5), `main_course` (18) |
| Тип страви | 159 | `dish` (68), `grain` (17), `combo` (42), `spread` (7), `fish` (2), `appetizer` (3), `beverage` (15), `dessert` (5) |
| Метод приготування | 24 | `none` (2), `blending` (7), `salting` (1), `smoking` (1), `grill` (1), `mixing` (1), `poaching` (6), `toasting` (1), `brewing` (4) |

Кількості перетинаються: один рецепт може мати кілька старих значень.
`cuisine = null` у цих записах допустиме й не є причиною їх потрапляння у вибірку.

Рецепти 228, 240, 249, 567, 573 мають `category = salad`, але `type = combo`.
Міграція зберегла конфліктні значення, тому поточний фільтр типу `salad` їх
не вибирає. Автоматично прирівнювати `dish` до основної страви, `grain` до каші
або всі `combo` до одного типу не можна без перегляду рецептів. Частина методів
і типів також може вимагати розширення списків; це окреме рішення користувача.
Розширений другий SELECT отримано й переглянуто: 177 унікальних рецептів,
57 старих категорій, 156 старих типів, 24 старі методи. ID 883, 886, 899
відсутні в новій вибірці; причина невідома, пропозиції їх не охоплюють.

У [таблиці для погодження](recipe-classification-review.md) наведено пакет A:
100 конкретних змін типу, категорія «Напої» для 12 записів із порожнім
полем і `grill` → `grilling` для ID 571. Це 112 різних рецептів.
Моделювання на наданих даних залишає 118 записів у postflight через інші
старі значення; пакет A не завершує всю перекласифікацію. Прогалини списків
і п'ять неоднозначних записів описані окремо. Наступний крок — погодити
цей конкретний пакет перед підготовкою нової міграції. Після аналізу дані
рецептів і списки в інтерфейсах не змінювалися.
